# Organisation users and settings

All paths use `/api`. Authenticated mutations require the session cookie, exact Origin and `x-csrf-token`. Organisation administration requires an active MFA-verified administrator, rechecked inside the tenant configuration transaction. Role remains employee/agent/admin; `approverEligible` and `isVp` are separate eligibility flags.

`UserProfile` is `{id,name,email,role,approverEligible,isVp,managerId,homeDepartment,phone,jobTitle,active,revision,createdAt,updatedAt,invitedAt,invitationPending}`. Dates are ISO strings; managerId and invitedAt may be null. Password hashes, MFA secrets and invitation hashes are never returned.

- `GET /admin/users` → `{users:UserProfile[]}`.
- `POST /admin/users` accepts `{name,email,role,approverEligible,isVp,managerId,homeDepartment,phone,jobTitle}`. Creates an inactive account, then returns `{user:UserProfile,invitation:{url,expiresAt}}`. Email normalizes to lowercase. Manager must already be active in the organisation. VP requires approval eligibility.
- `POST /admin/users/:id` accepts the create fields plus `{active,revision}` → UserProfile. Stale revisions return 409 with current public values. Another administrator must change the acting administrator's access/email. Retains at least one active admin; protects unresolved assignments, triage staffing, queue owner/substitute references, direct reports, pending approvals and active delegations. Security-sensitive changes revoke sessions; agent demotion/deactivation clears memberships. Changing a user's manager atomically invalidates previous approvals and re-evaluates their nonterminal service requests, with ticket revision changes. Re-activation uses a new invitation.
- `POST /admin/users/:id/invite` accepts `{revision}` → `{user,invitation}` for inactive users only. Supersedes any earlier link.
- `GET /profile` and `GET /users/:id` → UserProfile plus `{tickets:[{id,number,summary,state,createdAt,updatedAt}],limitReached}`. Employees access their own profile; agents and administrators access organisation profiles. Ticket history is independently permission-filtered, maximum 200; administrator status grants no private ticket access.
- `POST /auth/password` accepts `{currentPassword,newPassword}` → `{ok:true}` and revokes all current sessions. New passwords require 12–256 characters. Existing enrolled MFA remains enrolled.
- `POST /auth/activate` is public but requires exact Origin. Accepts `{organisation,token,password}` → `{ok:true}`. Tokens are 32 random bytes, expire after 48 hours, and only their SHA-256 hashes persist. Tenant and expiry are checked again when atomically consuming the token. Activation does not create a session. An enrolled administrator's MFA is preserved.

The invitation URL is `${APP_ORIGIN}/#activate?token=...&organisation=...`. Tokens remain in the fragment, avoiding HTTP request logs. The administrator receives the link once for secure manual handoff; responses also include `emailQueued:true`. Invitation email queues atomically with the user change in a tenant-scoped outbox. Its URL is encrypted with AES-256-GCM using the API/worker secret and tenant/user associated data. No plaintext link persists. The worker rechecks tenant activity, current user invitation hash, inactive account and expiry before SMTP delivery. Superseding, revoking, activating or sending an invitation clears stored ciphertext. The local development destination is Mailpit. Never place invitation URLs in tickets, audit records or application logs.

SMTP failures retain the encrypted payload and retry after 30 seconds, doubling to one hour, for at most ten attempts. Exhausted deliveries become skipped; an administrator can issue a new invitation. A stable Message-ID and durable sent state prevent ordinary repeated sends; an ambiguous SMTP acknowledgement or crash before committing sent state can produce duplicate email. The token remains single-use. Workers require the same `MFA_ENCRYPTION_KEY` as the API. Rotating that key requires draining/reissuing pending invitations as well as handling enrolled MFA secrets. Delivery integration checks run with `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM` and `MAILPIT_URL` set for the local SMTP capture service.

- `POST /admin/users/import/preview` accepts `{csv}` (maximum 100,000 characters and 100 users). Required headers `name,email`; optional `role,approverEligible,isVp,managerEmail,homeDepartment,phone,jobTitle`. Role defaults employee, booleans default false and otherwise accept exactly true/false. Managers must already exist and be active. RFC 4180 quoting, embedded commas/newlines and UTF-8 BOM are supported. Unknown/duplicate headers and malformed quoting fail. Returns `{rows:[{row,user,errors}],valid,previewToken,expiresAt}`. Invalid rows do not persist anything. No invitation secrets are generated until commit.
- `POST /admin/users/import/commit` accepts `{previewToken}` → `{users:[{user,invitation}]}`. Explicit commit uses a single-use preview bound to the administrator's tenant, account and session, expiring in ten minutes. All users persist atomically; current email/manager constraints are rechecked. Previews are in process memory, so restart requires another preview. A failed commit requires another preview. No partial import.
- `GET /admin/settings` returns `{id,name,brandName,timezone,locale,primaryColour,incidentPrefix,requestPrefix,defaultPriority,defaultSeverity,revision}`.
- `POST /admin/settings` accepts those fields except id and returns updated settings. Validates IANA timezone/locale, six-digit hex colour, distinct uppercase letter/digit number prefixes, P1–P5 priority and S1–S4 severity. Number prefix changes affect new tickets only. Configuration updates are audited and revision-protected. Business hours, holiday calendars and configurable attachment policy remain separate follow-up settings.
