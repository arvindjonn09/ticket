# Astrama

A configurable service desk for organisations, with incidents, service requests, approvals, organisation administration, invitations, protected attachments and email delivery on React, NestJS, Prisma and PostgreSQL. Product scope and verification are tracked in [update-plan.md](update-plan.md) and [delivery status and agent activity](docs/task-status.md#agent-activity).

## Run the local demo

Requires Docker Desktop with Linux containers.

Before the first run, copy `.env.example` to `.env` and set `MFA_ENCRYPTION_KEY` to a private 64-character hex value generated by `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Keep this key stable: it encrypts administrator authenticator secrets. The current local workspace already has a generated key in its ignored `.env` file. For a copied checkout, generate a new key before enrolling administrators.

```sh
docker compose up --build -d
docker compose ps
```

Open **http://localhost:4310**. The setup service bootstraps the restricted runtime database role, applies migrations and seeds two fictional organisations. PostgreSQL data persists in the `astrama-local_astrama-db` volume.

Local emails are captured at **http://localhost:4312**; they are not sent to real mailboxes. Private file storage and ClamAV run as separate containers. The scanner may take several minutes on first start; uploads fail safely until scanning is available. The API checks ticket and attachment permissions on every download.

Try this flow:

1. Sign in as Harbour's employee and report a Devices & workplace issue.
2. Sign out and sign in as Harbour's support agent. Open the issue, assign it to yourself, and reply.
3. Add an internal work note and resolve the incident with an internal resolution and customer summary.
4. Sign back in as the employee. Check the public conversation and confirm the fix or reopen the incident.
5. Sign in to Northstar and verify Harbour's records are unavailable.

The interface supports light, dark, and system appearance. Company and product names come from stored tenant data. Seeded examples are fictional.

## Organisation setup

The product team provisions organisations with the [provisioning command](docs/operations.md). The organisation administrator maintains their own users, routing, request catalogue and approval policies. Public signup is disabled.

After migration and seed, use `admin@demo.test` with the same local demo password in either organisation. First sign-in requires enrolling an authenticator: click **Begin setup**, choose **Add account / Scan QR code** in your authenticator app, scan the displayed QR and enter its current six-digit code. **Can't scan?** expands the manual setup key and URI. QR generation happens locally in the browser, without sending the secret to a QR service. Later sign-ins require the current authenticator code as well as the password. Configuration remains unavailable until MFA succeeds. Re-running the seed preserves existing MFA enrolment. Recovery/reset and key rotation are not exposed in the current UI.

Configure in this order:

1. Use **Manage section → Users** to invite users individually or preview/import a CSV. Activate invitations from the local mailbox or the private one-time link. Assign managers and approval eligibility as needed.
2. Create support groups and select active support agents as members, with a queue owner and substitute. For now each department is its own assignment group.
3. Create categories, choose applicable ticket types and their default support group.
4. Add subcategories with either **Inherit category group** or a specific routing group.
5. Use **Request catalog & approval policies** to configure items, prices, currencies, manager/VP approval and alternates. Employees use **Request a service**; eligible approvers use **My approvals**.
6. Check **Routing preview**, then submit an incident or request. Existing tickets retain their routing until an explicit correction or transfer.

Mapping changes apply to new incidents. Existing incidents keep their recorded destination. Archive categories/subcategories to stop new use while preserving history; deletion is limited to unused records. Removing a member who still owns unresolved tickets is blocked until that work is reassigned or resolved.

## Checks and development

Node 24 and pnpm 10.34.9 are used. Dependency versions are locked in `pnpm-lock.yaml`.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
```

Database-backed tests need the local database running and the runtime/owner connection strings from `.env.example` exported in the test shell; without both URLs the integration suite is skipped. Service checks also need the documented SMTP, object-storage and scanner environment. Stop the shared worker during API integration tests; the opt-in `RUN_QUEUE_TESTS=true` check starts its own dispatcher. Browser tests use the running application at `http://localhost:4310` and require the worker for recovery email: `docker compose up -d --no-deps --wait api web worker`. Install browsers with `pnpm exec playwright install chromium firefox webkit`; set `BROWSER_MATRIX=1` to run all three, or use the default Chromium run. `PLAYWRIGHT_CHROMIUM_PATH` can select an existing compatible Chromium executable. Test seed and credentials are for local development only. Do not run demo seeding against real customer data.

For local source development, start `docker compose up -d db`, export the `.env.example` values in your shell, run `pnpm db:bootstrap`, `pnpm db:migrate`, `pnpm db:seed`, and `pnpm dev`. Bootstrap must precede the first migration on a fresh cluster. Database grants are versioned migrations, so non-demo installations run bootstrap/migrations and the [new-organisation provisioning command](docs/operations.md), without running the demo seed. Source edits to shared packages require rebuilding them; API source changes require recompilation in this initial development setup.

## Scope

The local application covers incident and service-request creation, category/subcategory routing, caller-on-behalf, group claiming and lead assignment, triage, holds, cancellation, public/internal activity, resolution and fulfilment. Sequential manager/VP decisions, dated delegation and material-change invalidation protect request approval. Tenant-aware persistence, RLS, optimistic concurrency and audited configuration remain part of the foundation.

Organisation administration includes MFA, user invitations/CSV import, lifecycle protections, profiles, branding/timezone/defaults, groups and catalogue policies. Ticket attachments support broad formats with mandatory ClamAV scanning, a 5 MiB file limit, 10 files/50 MiB per ticket and protected downloads. Reports show permitted records, calendar-time metrics, CSV export and internal resolution search. Ticket mail uses a pg-boss worker and durable delivery records; invitations use an encrypted durable outbox. SMTP acceptance followed by a crash can duplicate email; retries do not repeat ticket actions.

After seeding, `manager@demo.test` and `vp@demo.test` use the demo password. The sample catalogue contains a manager-approved application request and a manager-plus-VP equipment request. These examples are configurable; no real company approval threshold is assumed.

Organisation setup also includes business-day approval reminders/escalations, resolved-incident closure, file limits, retention/legal-hold policy and service health. Password recovery uses an encrypted durable queue; login throttles and CSV previews are shared across API instances. Owner tools support verified MFA recovery, key rotation, tenant export/deletion and encrypted database-plus-object backups with isolated restore verification.

See [production deployment](docs/production-deployment.md), [account recovery](docs/recovery.md), [data lifecycle](docs/data-lifecycle.md), [automation](docs/automation.md) and [complete backups](docs/backup-recovery.md). Real hosting/DNS/certificates/mail, offsite backup configuration, customer policy selection, SLA commitments and customer pilot sign-off remain deployment work. SSO, automatic email intake and customer-specific integrations remain later features. The [delivery status](docs/task-status.md) records actual verification.

Organisation-specific requests will use tenant settings and selectively enabled features/integrations in one maintained codebase. Arbitrary integration installation is not implemented by this slice.
