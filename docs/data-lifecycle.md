# Tenant data policy and operator lifecycle

Implements plan sections 21 (scripted, audited tenant export/deletion) and 24 decision 14 (configurable retention; no automatic deletion before customer agreement).

Organisation administrators with current enrolled MFA can edit **Data and attachment policy**. Settings changes use revisions, tenant RLS, live user/session checks and configuration audit. They grant no additional ticket content permission. API endpoints: `GET /api/admin/data-policy`, `POST /api/admin/data-policy` (session and CSRF required).

New organisations and missing policy rows default to scanned broad file formats, 5 MiB/file, 10 files/ticket, 50 MiB/ticket and disabled retention. An empty extension list allows all formats subject to scanning; otherwise only the final, case-insensitive filename extension is allowed. Extension filtering is an additional restriction, not proof of content type. Uploads remain privately stored as octet streams, scanned and subject to ticket audience/terminal-state permissions. Policy is checked before scanning and again under the ticket lock before committing. Existing attachments are preserved when limits tighten. The multipart infrastructure cap stays 5 MiB per file; the tenant may choose a lower cap, 1-100 files and up to 500 MiB combined per ticket.

Retention classes are tickets/messages, attachment objects and ticket audit history. Blank days disable that class; all three must have periods before aggregate deletion is eligible. Only Complete, Cancelled and Rejected tickets qualify. The ticket's last update must predate the longest configured period. Newer attachment/audit creation dates also protect their class periods. A retained duplicate reference protects its target. Any tenant or class legal hold blocks retention and full tenant deletion. Organisation configuration audit and operator audit do not expire through ticket retention. Account records are retained for referential history and only removed through explicit organisation deletion; backup expiry is a separately managed deployment operation. No scheduler invokes destructive retention. Configuring days never schedules deletion.

Use the trusted migration-owner connection only from a protected operator environment. Runtime application credentials cannot read the content-free operator ledger or deletion manifests and cannot execute these owner operations. Set `MIGRATION_DATABASE_URL` and the existing private storage environment (`S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, optionally `S3_REGION`). Do not print credentials or put tokens/customer content in reasons: `--evidence` is a support authorization reference, not the authorization document or secret. The caller is a trusted operator; this CLI does not independently verify a support ticket in an external system.

Build the API and shared packages first. Commands below use `node apps/api/dist/operator-data.js` from the repository root. Replace placeholders with a specifically authorized tenant and exact slug. All commands require `--tenant`, `--expected-slug`, `--operator`, `--reason` and `--evidence`; malformed or repeated options fail closed.

```text
node apps/api/dist/operator-data.js export --tenant <uuid> --expected-slug <slug> --operator <operator-name> --reason "Customer-authorized export" --evidence SUPPORT-123 --output <new-private-directory>
node apps/api/dist/operator-data.js retention --tenant <uuid> --expected-slug <slug> --operator <operator-name> --reason "Approved retention run" --evidence SUPPORT-123
node apps/api/dist/operator-data.js retention --tenant <uuid> --expected-slug <slug> --operator <operator-name> --reason "Approved retention run" --evidence SUPPORT-123 --execute
node apps/api/dist/operator-data.js delete --tenant <uuid> --expected-slug <slug> --operator <operator-name> --reason "Customer-authorized deletion" --evidence SUPPORT-123
node apps/api/dist/operator-data.js delete --tenant <uuid> --expected-slug <slug> --operator <operator-name> --reason "Customer-authorized deletion" --evidence SUPPORT-123 --execute --offline
```

Export is an explicit read operation; delete and retention default to preview. Preview makes no persistent changes. Inspect its tenant identity, counts/eligible ticket IDs and legal holds before separately running with `--execute`. Take and verify the appropriate protected recovery backup before destructive work, according to the deployment's approved backup and erasure policy.

Exports contain a consistent tenant business snapshot while holding the same tenant configuration lock as normal ticket/configuration writes (Read Committed observes holds committed while the operator waits for that lock), plus the matching immutable attachment objects. An explicit business table allowlist includes organisation/users (safe user columns only), groups/memberships, routing/categories/subcategories, counters, request items, tickets/messages/internal work notes, approvals/delegations, ticket/configuration audit, attachment metadata, data policy and automation settings/actions. It excludes all sessions, credentials/password hashes, MFA secrets/state, invitations/encrypted URLs, password recovery records, authentication throttles, idempotency, dispatch/outbox/delivery state, CSV import previews and platform heartbeats. This is a trusted support export with internal customer content, not an employee-facing CSV or a security/database backup. Future business tables need an intentional allowlist update.

Choose a private, nonshared parent directory outside the checkout, owned and controlled by the trusted operator. Other users must not be able to replace or delete children in that parent (including Windows DELETE_CHILD permissions); the CLI trusts this operator-selected parent. The export directory must not already exist. It is created with owner-only permissions (0700/0600 on Unix; inherited ACLs removed and only the current Windows identity granted access). Files use UUID names; customer filenames remain metadata. `manifest.json` lists file paths, byte sizes and SHA-256 hashes for records and every attachment. Missing objects, invalid tenant keys or size mismatches fail the export. Failed partial outputs stay private for inspection; they are not complete exports. Remove them according to the approved support-artifact policy, then retry into a new directory. The current command buffers the snapshot and one attachment in memory, holds a tenant lock for at most five minutes and should run during a suitable maintenance window; stream large snapshots when measured tenant size requires it.

Full deletion requires stopping API ingress and all background writers first, including draining in-flight uploads, then asserting `--offline`. This is an operator assertion, not a process detector. Keep writers stopped until completion. The command validates exact UUID/slug and holds, disables the tenant, revokes every tenant session and durably stores the attachment-key retry manifest before deleting objects. It deletes known attachment keys and all private objects under the exact `<tenant-uuid>/` prefix, including orphaned uploads; no foreign prefix is accepted. Database rows are removed in FK order only after private object cleanup succeeds. Recovery/import preview records cascade on user/session deletion; automation records are explicitly removed. Queue jobs contain only references; current tenant existence/status checks make stale jobs inert.

If storage fails, the tenant remains disabled and sessions revoked, business rows and the retry manifest remain, and a failure outcome is audited. Correct storage access and rerun the same tenant/slug `delete --execute --offline` command: object deletion is idempotent. The manifest is erased only with successful database cleanup; a permanent content-free audit records operation/operator/reason/reference, tenant UUID/slug, timestamps, count and outcome outside the tenant FK graph. Keep failed tenants offline. A final database failure likewise leaves retryable state. Repeating a fully completed deletion fails tenant lookup; inspect the durable completion audit instead of recreating the tenant.

Retention holds the tenant lock across object removal and database cleanup; a partial storage failure retains database metadata and is safely retryable by rerunning the explicit command. Some objects may already have disappeared during a failed attempt, so inspect failure audits promptly and finish the retry. It removes associated notification/idempotency/automation references along with ticket content and audit, preserving surviving users/configuration. Disabled or held tenants are refused. All successful executed requests and outcomes, and failed attempts, are recorded in the operator ledger.

Deletion of live storage does not erase earlier backups, exported support artifacts or externally delivered email. The deployment owner must track and expire those copies under the approved policy; restore procedures must honour durable deletion evidence before reopening restored data. Keep operator evidence protected and retained separately from the customer data being erased.

## Runnable verification

With disposable local PostgreSQL/storage/scanner configured, build shared packages/API, then run:

```text
pnpm --filter @astrama/api exec vitest run test/data-lifecycle.integration.test.ts --fileParallelism=false
```

The check creates fresh random test tenants only. It verifies MFA and cross-tenant denial, runtime owner-operation denial, policy limits through scanned HTTP uploads, secret-free exports and manifest hashes, disabled/held retention, preview without mutation, actual terminal aggregate retention, and a real S3 deletion failure followed by a safe retry with foreign objects preserved. It never deletes the existing harbour/northstar tenants.
